## Context: why this review happened

You came out of ~7 rounds of visual iteration on the Don't Be a Stranger (DBAS) page
that kept circling without landing. The instinct going in was that this needed more
design polish, or a tech-stack change. Having read everything, I don't think either is
true. Two things in the evidence changed my mind:

1. **This exact failure has already happened once before**, on the *old hand-coded HTML
   site*, a month before this Astro rebuild even started (see `looks-a-bit-better-glowing-aho.md`
   and `users-...-locket.md` in the plan history: "the page is a mess... restructure it
   from zero," on plain HTML, no Astro in sight). The same page, on two completely
   different technology stacks, converged on the same complaint both times. That rules
   out the tools as the cause.
2. **Round 7's own audit already suspected this.** It found and fixed real bugs (a
   `display:grid` stretching bug, a padding bug shared by all three case studies), then
   explicitly declined to consolidate the 9+ accumulated visual patterns "unless the
   audit doesn't resolve the flow complaint" — i.e. the session doing the fixing was
   already suspicious that pattern proliferation, not any single defect, was the real
   issue.

**The actual mechanism**, as best I can reconstruct it: every round has been
presentation-only. The approved body copy (locked since session A4) has never moved.
Feedback has consistently been about *feel* — "boring," "flat," "doesn't feel like my
style" — which is not a target you can hit by fixing named, nameable things (a crop, a
caption, a component) one at a time, because "feel" isn't decomposable that way. Each
round fixed something real and specific, and the holistic complaint carried over anyway,
because the actual gap was structural: **the page has no skimmable layer**. It's ~1,850
words of genuinely excellent, specific, sensory prose — closer to thesis writing than to
a UX case study — with no TL;DR, and its Outcome/Learnings facts sit at the very bottom,
after the full narrative. A 90-second reader hits paragraph one of "The idea" and either
commits to reading or leaves; there's nothing built for the leave-early path to still
land the point.

Compare this to your own Ericsson page, which already solves this: each of its three
sub-cases opens with a one-line TL;DR ("One line: our developers used AI to turn Figma
into code, but it kept building the annotations instead of the interface..."), has a
case-switcher, and the outcome numbers are teased before the reader commits to any one
case. Nobody had to invent that pattern for this replan — it's already live, ten feet
away from the page that's been stuck.

**So: the underlying work is good, and I'm not proposing to rewrite the DBAS narrative,
the thesis grounding, or the visual language.** What's missing is a shared, falsifiable
definition of "done," and a structural (not decorative) fix to the one page that's stuck.

## The tech/template question, answered directly

I evaluated three real alternatives before ruling them out, not just defended the status
quo by default:

**Framer.** Genuinely the strongest no-code option for a solo designer's portfolio in
2026 — visual, motion-native, fast to a first result, and it's what a lot of designers
reach for exactly for this reason. I'm not recommending it, because it would cost more
than it fixes: your content currently lives in typed Astro content collections with a
schema that has already caught two real bugs (a hardcoded outcome/learnings bug, a wrong
institution count) purely because the schema made the mistake impossible to render
silently. Moving to Framer means giving that up — content becomes per-page visual
placement again, with no schema to catch the next factual slip. It also doesn't fix the
actual failure mode: nothing about Framer would have stopped round 8 from being "let's
try one more treatment for this quote." If anything, a visual builder makes ad hoc,
per-page tweaking *easier*, not harder.

**Webflow.** Same conclusion, more so — it's the right tool once you have "dozens of
articles, categories, or dynamic pages," which is not this site (5 pages, 3 of them deep).
It would be trading a system you already have (git history, typed schema, zero-JS
default) for a system built for a scale problem you don't have.

**Astro, unchanged, but with a formalized component contract.** This is what I'm
recommending. Your `global.css` is already genuinely well-built — a real fluid type
scale (Utopia method), systematic spacing, disciplined color tokens with contrast-safe
`-ink` variants. That was never the problem. What's missing is *governance*: patterns
have been added per-round, ad hoc (plate captions, card-stacks, lens disclosures,
museum-blocks, ink-grids — 9+ of them), and `DESIGN-SYSTEM.md` — which is supposed to be
the documented contract — hasn't been updated since session B6 and is now stale relative
to the actual CSS. The fix isn't a new platform, it's finishing what round 7 already
started: audit the pattern list down to the ones that earn their keep, freeze that set,
and treat `DESIGN-SYSTEM.md` as load-bearing (no new one-off visual pattern ships without
being added to it first). You already have the discipline for this — it's the same
instinct that built the fact-checking pipeline for the thesis claims. It just hasn't been
applied to the visual layer yet.

If you want a lighter-weight way to get the "structured, future-proof" feeling without
adopting new infrastructure: you have Figma MCP access in this environment. Once the
closed component set is decided, it's worth designing it as one real Figma page (a
literal one-page "Nikos Saoulidis Design System" file) *before* touching more case-study
layout — reviewing the system as a system, not per-page, is exactly the review altitude
that's been missing.

## The two audiences, and which machine-readability mechanism actually matters

You named three candidate mechanisms for "parsable for agents." I ranked them by actual
leverage rather than treating them as equal:

1. **Schema.org Person (site-wide) + CreativeWork (per case study) JSON-LD — do this.**
   This is the only one of the three with a *proven* consumer: Google's rich results
   read it today, and current evidence (structured data / schema markup showing up
   disproportionately in AI-search citations) suggests it's also what tools like
   ChatGPT and Perplexity lean on when deciding what to cite and summarize. It's also
   the same shape ATS and recruiting tools want. One mechanism, three payoffs.
2. **llms.txt — add it, but as a footnote, not a pillar.** It's a real, live convention
   (llmstxt.org; Anthropic, Cloudflare, Supabase, Vercel all publish one), but as of this
   research, no major LLM provider actually reads it at inference time — it's mainly
   consumed by AI *coding* tools reading docs. For a 5-page portfolio it costs almost
   nothing to add (this is already B12 in REBUILD-PLAN.md), so do it, but don't let it
   absorb real design effort or get treated as solving the "AI summarizes me correctly"
   goal on its own.
3. **An embedded on-site assistant — correctly parked, leave it parked.** CHAT-CONCEPT.md
   already defers this to after cutover, and I agree with that sequencing for a reason
   beyond "it's not built yet": your own target reader skims for 90 seconds. That reader
   is not going to open a chat widget and start typing — they're going to read. A chat
   assistant serves a *different*, lower-frequency reader (someone already invested
   enough to ask follow-up questions), so it's additive polish once the core site is
   converting attention on its own, not a fix for the current convergence problem. Build
   it later; don't let it compete with DBAS or machine-readability for this cycle's
   attention.

Concretely: **skip building a chat assistant this cycle.** Ship schema.org structured
data (cheap, proven, dual-purpose for search and ATS tools) and llms.txt (near-free) as
the machine-readable layer; leave the chat idea exactly where CHAT-CONCEPT.md already
put it.

## The DBAS fix, specifically

Not a rewrite. Two structural moves, both aimed at the 90-second reader, neither
touching the approved narrative prose:

1. **Move a condensed outcome strip up, near the top.** Right now "Still running since
   May 2025," "built with five named staff across two museums," and the visitor quotes
   are the *last* thing on the page, after ~1,850 words. A recruiter who skims for
   outcomes never sees them. Add a short fact strip immediately after the existing
   at-a-glance block (Role/When/Where/Worked With) — something like *"Live since May
   2025 in two Gothenburg museums · tested with 25 people across 3 field rounds · still
   running, no end date"* — so the payoff is visible before anyone commits to the full
   narrative. The full Outcome/Learnings sections stay at the bottom for whoever reads
   all the way through; this doesn't replace them, it previews them.
2. **Add one line at the very top that does what Ericsson's "Three cases I'm proud of..."
   line does** — a single sentence stating what the project is and why it matters,
   before "The idea" section starts its slow, deliberate narrative build. The narrative
   voice is a strength; it just can't be the *only* entry point for a reader with 90
   seconds.

**Definition of done for this round** (replacing "does it feel like my style," which
isn't falsifiable): a reader who reads only the standfirst, the new fact strip, and the
new one-liner should be able to state the problem, your role, and the outcome correctly.
Test it by asking someone who hasn't seen the page to do exactly that. If it passes,
stop — don't open another decorative round behind it.

**A stop-rule for future rounds, on any page:** if two rounds of visual/decorative
changes don't resolve a "doesn't feel right" complaint, the next round changes structure
(what's included, what order, what's a skim-layer vs. a depth-layer), not decoration
(colors, crops, component choice). This is round 7's own instinct, made into a rule so
it doesn't have to be rediscovered per page.

## Addendum: upgrading the design-execution stack (added after your review)

You confirmed the core diagnosis (IA problem, not visual) and asked for one addition:
install and use **Impeccable** (impeccable.style) combined with **Anthropic's official
`frontend-design` skill**, synthesized with your existing personal identity, as the
standing design-execution stack for this project going forward. I researched both
before writing this in — neither is vaporware:

- **Anthropic's `frontend-design` skill** is real, official, in the `anthropics/skills`
  GitHub repo, installable in this Claude Code environment via
  `/plugin install frontend-design@anthropics/claude-code`. It's a decision-forcing
  process (purpose / tone / constraints / differentiation, before any code) built to
  stop AI-generated interfaces from defaulting to generic patterns — including, by name,
  banning common fonts like Inter as a lazy default.
- **Impeccable** (`github.com/pbakaus/impeccable`, 69.6k stars, Apache-2.0, maintained by
  Paul Bakaus) is an independent but legitimate, actively-maintained project that
  explicitly builds on top of `frontend-design`. It installs via `npx impeccable install`
  (targets Claude Code's `.claude/` folder among 17+ supported tools), adds a `/impeccable`
  command with subcommands (`init`, `audit`, `polish`, `critique`, `shape`, `typeset`,
  `colorize`, `layout`, `harden`, etc.), and creates `DESIGN.md` + `PRODUCT.md` at the
  project root plus a `.impeccable/` working directory.

**How the three layers resolve, per your answers:**

- **Layering order:** your personal identity (Bauhaus, Rams, the three-brand-color
  system, the DBAS-native visual language) is the aesthetic direction. `frontend-design`
  supplies the anti-genericness discipline and forced-decision process. Impeccable is the
  tactical command layer that runs audits/critiques against both.
- **Where identity and the skill stack might conflict** (the Inter-font case is the
  concrete example found this session): **case by case, not a blanket rule either way.**
  Concretely, that means: when `frontend-design`/Impeccable flags something already
  locked in, don't auto-apply the flag — surface it as a specific question ("here's what
  it's flagging and why, here's the reason we chose it originally, your call") rather
  than either silently overriding the skill or silently keeping the old choice. This
  applies per-decision, not as a standing exemption for the whole existing system.
  **Resolved for this specific case:** the body font changes from Inter to **EB
  Garamond**, kept paired with **Jost for display/titles**. EB Garamond is SIL
  Open-Font-Licensed (freely self-hostable, same legal footing as the current Jost setup,
  no Typekit-style licensing problem) and has a variable-font distribution, so it fits
  the existing self-hosted-variable-font approach without a build-process change. This is
  a real aesthetic shift worth naming explicitly, not just a token swap: a geometric-sans
  display paired with a classical serif body moves the site's feel from pure
  Bauhaus-geometric toward something more editorial, and it's worth a quick visual gut
  check once implemented (readability at body-text sizes, and whether it still reads as
  cohesive with the ink-grid/Mondrian visual language) rather than assuming the pairing
  is right just because both fonts are individually well-regarded.
- **Design-doc consolidation:** Impeccable's `DESIGN.md` becomes the one doc of record.
  `DESIGN-SYSTEM.md`'s still-accurate content (the token system, the component table
  once audited per the plan above) gets migrated into `DESIGN.md` during setup, and
  `DESIGN-SYSTEM.md` is then retired rather than kept as a second, competing source of
  truth. This replaces the earlier recommendation to just refresh `DESIGN-SYSTEM.md` in
  place — same underlying goal (one current, load-bearing design contract), now served by
  a maintained tool instead of a hand-maintained file.
